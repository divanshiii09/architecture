Gym Renewal Reminders

Four drawings of the same system, each answering one question a developer will actually ask before writing code: where does data flow, what decides who gets messaged, how does a freeze move a date, and what is stored.

  • Next.js on Vercel
  • Postgres on Supabase
  • WhatsApp Cloud API (Meta)
  • 1 owner · 2–5 branches
  • Reminders at −7d / 0 / +3d
  • ₹0 per month

Topology

What talks to what

Everything green is the message path — the only part of the system that reaches a member's phone. Note that nothing the owner does sends a message: the owner writes to the database, and a separate clock reads it. That separation is what makes the system work while the gym is shut.

  • One deployFrontend and backend are the same Next.js project, so there is no second server to run, secure or pay for.
  • Two entry pointsA human request (owner) and a scheduled request (cron) hit the same API layer. The expiry engine is shared, so the dashboard and the reminders can never disagree about a date.
  • TimezoneServerless cron fires in UTC. 03:30 UTC is the 09:00 IST slot — getting this wrong is the most common bug in this class of system.

Daily job

How the system decides who to message

This is the whole product in one flow. The two gates are what separate a system the owner trusts from one that spams paying members — the first catches members who already renewed, the second makes the job safe to run twice.

  • Dry run firstShip the endpoint with a ?dry=1 mode that logs who would be messaged. Check that list against the register by hand before ever letting it send.
  • Order mattersGate 1 before gate 2. Checking payment first means a renewal silently cancels the remaining 0 and +3 stages with no cleanup job.
  • Volume300 members × 3 stages is ~900 conversations a month worst case, inside Meta's free tier — and far lower in practice, because renewals cancel the later stages.

Date engine

Why a freeze moves all three reminders

The expiry date is never typed in — it is calculated from the cycle start, the plan length, and the days the member was frozen. Add a freeze and every downstream reminder shifts by itself. There is nothing to back-fill.

  • Cached, not storedKeep the result in members.expiry_date and recompute it on every write. The daily job then needs one indexed date lookup instead of a calculation across every member.
  • Still frozenA member with an open freeze is skipped by the job entirely — their clock isn't running, so they can't be expiring.
  • Open questionOn renewal, does the new cycle start from the old expiry date or from the day they paid? Both are one line; it decides whether late payers lose those days.

Data model

Five tables, one guard

Payments and freezes are kept as separate rows, not edited fields, so the history stays intact and the expiry date can always be recomputed from scratch. reminder_log is both the audit trail the owner reads and the lock that prevents duplicates.

  • Branch scopingmembers.branch_id is the only multi-branch concession needed. Dashboard counts and the member list filter on it; the reminder job ignores it.
  • DiscountsStored as type plus value on the member (the standing arrangement) and again on each payment (what was actually applied), so changing a rate later doesn't rewrite history.
  • Not in v1Member logins, online payment collection, attendance, trainers. The branches table and RLS are the seams those grow along.
